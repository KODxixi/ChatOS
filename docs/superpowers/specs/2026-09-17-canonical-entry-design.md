# 正式源码与运行入口收口

用户已授权执行前一轮提出的唯一真相治理；不再重复设计确认。

## 目标

共享规则定义职责而非强制所有仓库同一文件夹模板。每个组件/环境必须声明正式源码、构建、启动、数据边界和验收命令；构建身份与运行实例必须能核对。原型验收不等于正式集成。

## ChatOS 决策

- 唯一维护的新版 UI 源码归入主仓库 `apps/chatos-console`，来源为独立原型仓库 commit `e9d78e9c3f1c216c668a4810fe890d764131b88a`。保持现有视觉与交互，不重设计。
- 保留现有服务分工：前端 Node 运行于 3108，Python API 于 8912；统一 `scripts/start_chatos.bat` 入口。8912 的网页入口跳转同一新版，而非继续发布旧 UI。明确 3108 是正式 UI 服务，不再称匿名预览；3000 仅历史预览。
- 不为了单端口重写两套 API。原型现有只读 SQLite 适配保留；未接入正式后端的演示功能必须有明确标识，不将 mock 宣称为真实业务。
- 旧源码与原型仓库保留可恢复基线；不得删除数据库、重置水位、杀死未验证归属的进程。
- 构建生成含源码摘要、来源与构建版本的身份文件；正式启动检查源码追踪、配置目标及线上身份，端口占用不等于正确服务。
- 全局 PATHS 只注册仓库与入口指针，详细端口/构建事实由仓库维护；不复制成多处独立真相。

## 验收

共享治理校验通过或明确区分既有失败。ChatOS 新版正式源码受根仓库追踪；类型检查、构建与身份校验通过；正式启动网页可访问且返回同一构建；错误/过期构建与端口冲突能被拒绝。真实浏览器验证不可用时明确标记，不能用 HTTP 验证冒充视觉验收。

## 非目标

不批量重排所有仓库；不重写设计系统；不代办另一个后端任务；不外推、外发或修改用户数据库。
